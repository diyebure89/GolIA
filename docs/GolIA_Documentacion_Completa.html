1. Especificación de Requisitos de Software (IEEE-830)

1.1 Introducción

Propósito. Especificar los requisitos funcionales y no funcionales de la aplicación móvil GolIA, una plataforma de pronósticos deportivos de fútbol.

Alcance. GolIA permite registrarse, consultar partidos, realizar pronósticos de marcador exacto, acumular puntos, competir en un ranking global compartido entre dispositivos y leer noticias. Se compone de una app Android (cliente), un backend REST (Spring Boot + MySQL) y las integraciones con API-Football y NewsData.io.

Definiciones y acrónimos

TérminoDefinición
PronósticoPredicción del marcador exacto de un partido.
Marcador exactoResultado de goles local–visitante (ej. 2-1).
RankingClasificación de usuarios por puntos acumulados.
PeríodoVentana del ranking: Semanal (7d), Mensual (30d) o Total.
JWTJSON Web Token (autenticación por token).
RF / RNFRequisito Funcional / Requisito No Funcional.

1.2 Descripción general

Perspectiva del producto. Arquitectura cliente-servidor. El cliente Android consume una API REST propia (cuentas, pronósticos, ranking) y APIs de terceros (partidos y noticias). Los datos de cuenta y pronósticos residen en MySQL central, permitiendo acceso multi-dispositivo y un ranking consistente.

Características de los usuarios

PerfilDescripción
Usuario registradoAficionado que pronostica y compite. Conocimientos técnicos básicos.
Usuario invitadoVe contenido público (ranking) sin sesión; no pronostica.

Restricciones

  • Plataforma Android (minSdk 24, targetSdk 36).
  • Dependencia de conectividad para auth, pronósticos, ranking y datos externos.
  • Límite de peticiones de las APIs gratuitas de terceros.
  • Contraseña de mínimo 8 caracteres.

2. Metodología de Desarrollo

2.1 Metodología: Desarrollo por Prototipos (evolutivo)

Se seleccionó la metodología por prototipos de tipo evolutivo, dentro de un marco iterativo e incremental.

Justificación

  • Requisitos que se refinan con el uso: las reglas de negocio (puntuación, períodos, bloqueo) se afinaron al observar el comportamiento real.
  • Validación temprana de la interfaz: construir pantallas funcionales permitió validar la experiencia antes de la lógica completa.
  • Integraciones inciertas: las APIs externas y el backend propio se integraron de forma incremental.
  • Evolución del prototipo: cada prototipo se refinó hasta ser el producto final (no desechable).

Carácter evolutivo: sobre una arquitectura por capas estable, la capa de datos evolucionó de almacenamiento local (Room/SQLite) a un backend remoto (Spring Boot + MySQL) cambiando solo las implementaciones de repositorio, sin tocar la interfaz ni el dominio.

2.2 Ciclo de vida aplicado

1. Recolección y refinamiento de requisitos
          ↓
2. Diseño rápido (pantallas + modelo de datos)
          ↓
3. Construcción del prototipo (iteración N)
          ↓
4. Evaluación (pruebas + feedback)
          ↓
5. Refinamiento  ──► (vuelve al paso 1 si hay cambios)
          ↓
6. Producto final (prototipo consolidado)
